# Методика расчёта Repo Health Score

Документ описывает, как Pulse вычисляет Repo Health Score. Описание полное: по нему расчёт
можно повторить на тех же входных данных. Все константы взяты из исходного кода движка
оценки (`src/lib/scoring/`), основной файл — `src/lib/scoring/config.ts`. Та же методика с
текущими значениями констант опубликована на странице `/methodology` демонстрационного стенда.

## 1. Общие принципы

1. **Шкала.** Итоговая оценка и оценки категорий — числа от 0 до 100.
2. **Детерминированность.** Движок оценки — чистая функция `scoreRepo(facts) → result`
   (`src/lib/scoring/index.ts`). Он не обращается к сети и базе данных. Одинаковые факты дают
   одинаковый результат.
3. **Отсутствие данных не равно плохому результату.** Метрика без данных получает статус
   «нет данных» и исключается из расчёта. Её вес перераспределяется между измеренными
   метриками (раздел 4).
4. **Опора на факты.** Каждая метрика хранит исходное значение и текстовую расшифровку
   («Коммитов за 90 дней: 14»). Они показываются рядом с баллом.
5. **Безопасность — только по SourceCraft AppSec.** Собственное сканирование в балл
   безопасности не входит (раздел 3.1).

## 2. Категории и веса

Используются все шесть категорий из раздела 3.1 технического задания. Веса совпадают с
ориентиром ТЗ.

| Категория | Ключ | Вес `W` |
|---|---|---:|
| Безопасность | `security` | 0,20 |
| Код и технический долг | `code` | 0,20 |
| Активность проекта | `activity` | 0,15 |
| Документация и лучшие практики | `docs` | 0,15 |
| CI/CD | `ci` | 0,15 |
| Задачи (issues) | `issues` | 0,15 |
| **Итого** | | **1,00** |

## 3. Метрики

### 3.0. Функции нормализации

Сырые значения переводятся в шкалу 0–100 четырьмя функциями (`src/lib/scoring/normalize.ts`):

| Функция | Формула |
|---|---|
| `linear(x; min, max)` | `clamp(100 · (x − min) / (max − min))` |
| `inverted(x; best, worst)` | `clamp(100 − 100 · (x − best) / (worst − best))`: меньшее значение лучше |
| `log(x; target)` | `0` при `x ≤ 0`; `100` при `x ≥ target`; иначе `100 · ln(1 + x) / ln(1 + target)` |
| `bool(x)` | `100`, если признак есть, иначе `0` |

`clamp` ограничивает значение отрезком [0; 100].

В таблицах ниже `w` — вес метрики внутри категории. Сумма весов в каждой категории равна 1.
Столбец «Цель» — значение, до которого метрику подтягивает рекомендация (раздел 7).

### 3.1. Безопасность (`security`)

Источник — открытые находки SourceCraft AppSec (SAST, SCA, secret scanning): последний скан
(`/v1/scans/latest`) и группы дефектов (`/v1/defect-groups`).

| Метрика | `w` | Расчёт | Цель |
|---|---:|---|---:|
| `security.critical_vulns` | 0,35 | `inverted(N_critical; 0, 3)` | 100 |
| `security.high_vulns` | 0,25 | `inverted(N_high; 0, 10)` | 100 |
| `security.medium_vulns` | 0,15 | `inverted(N_medium; 0, 25)` | 100 |
| `security.secrets` | 0,25 | `bool(N_secrets = 0)` | 100 |

**Когда данных нет.** AppSec отдаёт результаты только участникам репозитория. Поэтому:

- у публичного репозитория в публичной оценке все четыре метрики имеют статус «нет данных»,
  и категория выпадает из итога одинаково для всех репозиториев рейтинга;
- у приватного репозитория, оценённого токеном владельца, категория считается по AppSec;
- владелец публичного репозитория видит свою оценку с учётом AppSec отдельно, в блоке
  «Видно только вам». В рейтинг и бейдж эта оценка не попадает (раздел 6).

Проверка зависимостей по открытой базе OSV.dev и поиск строк, похожих на ключи, в истории
коммитов показываются на странице анализа как справка с пометкой «не SourceCraft AppSec».
На балл они не влияют.

### 3.2. Код и технический долг (`code`)

Источник — git-клон репозитория (до 1500 файлов исходников, файлы больше 200 КБ и
сгенерированные файлы пропускаются) и дерево файлов из API.

| Метрика | `w` | Расчёт | Цель |
|---|---:|---|---:|
| `code.tests` | 0,24 | `linear(T; 0, 25)`, где `T` — файлов тестов на 100 файлов исходников. Если исходники прочитать не удалось: `bool(есть каталог тестов)` | 60 (100 для запасного признака) |
| `code.file_size` | 0,14 | `inverted(L; 5, 40)`, где `L` — доля файлов длиннее 500 строк, % | 70 |
| `code.comments` | 0,07 | `linear(C; 0, 12)`, где `C` — доля строк-комментариев, % | 60 |
| `code.todo_debt` | 0,08 | `inverted(D; 0,5; 8)`, где `D` — пометок TODO, FIXME, HACK, XXX на 1000 строк | 70 |
| `code.has_linter` | 0,11 | `bool(есть конфиг линтера)` | 100 |
| `code.lockfile` | 0,11 | `bool(есть lock-файл)` | 100 |
| `code.dependency_bot` | 0,08 | `bool(настроен Dependabot или Renovate)` | 100 |
| `code.build_manifest` | 0,07 | `bool(есть манифест сборки: package.json, pyproject.toml, go.mod и т. п.)` | 100 |
| `code.gitignore` | 0,06 | `bool(есть .gitignore)` | 100 |
| `code.editorconfig` | 0,04 | `bool(есть .editorconfig)` | 100 |

**Оценка модели.** Если ИИ-ревью кода прошло успешно, категория `code` целиком
определяется его баллом. В ней остаётся одна метрика `code.ai_review` с весом 1. Порядок ревью:

1. Модель по списку путей (до 400) выбирает файлы, которые стоит прочитать.
2. Из выбранных файлов берутся фрагменты: до 12 файлов, до 4000 символов из каждого.
3. Модель оценивает фрагменты по пяти критериям: читаемость, структура, обработка ошибок,
   тесты, единообразие. Измеренные числа из таблицы выше передаются модели как факты.
   Пересчитывать их она не должна.

Если ревью не удалось (модель недоступна, ответ не прошёл проверку схемы, превышен
бюджет), категория считается по таблице выше. Причина показывается на странице анализа.
Код приватных репозиториев во внешнюю модель не передаётся: для них категория всегда
считается по таблице.

### 3.3. Активность проекта (`activity`)

Источник — история коммитов из клона (окно 90 дней, не более 2000 коммитов) и API
SourceCraft (релизы, теги, pull request).

| Метрика | `w` | Расчёт | Цель |
|---|---:|---|---:|
| `activity.commits_90d` | 0,24 | `log(N_commits_90d; 50)` | 60 |
| `activity.freshness` | 0,24 | `inverted(D; 0, 180)`, где `D` — дней с последнего коммита | 80 |
| `activity.active_authors` | 0,15 | `log(N_authors_90d; 5)` | 70 |
| `activity.bus_factor` | 0,13 | `S` — доля коммитов самого активного автора за 90 дней, %. При `S ≤ 30` — 100; иначе `100 − (S − 30) / 70 · 70`, то есть линейно до 30 баллов при `S = 100` | 80 |
| `activity.releases` | 0,13 | `log(N_releases + N_tags; 3)` | 100 |
| `activity.pr_flow` | 0,11 | `log(N_pull_requests; 10)` | 100 |

Нижняя граница bus factor — 30, а не 0. Проект одного автора — нормальный случай, и это
не должно обнулять категорию.

### 3.4. Документация и лучшие практики (`docs`)

Источник — дерево файлов из API, текст README из клона и карточка репозитория.

| Метрика | `w` | Расчёт | Цель |
|---|---:|---|---:|
| `docs.readme` | 0,28 | 0, если README нет. Иначе сумма: 20 за наличие; +30, если длина ≥ 400 символов; +30, если заголовков уровня 1–3 не меньше трёх; +20, если есть раздел об использовании (usage, examples, getting started, «использование», «примеры», «быстрый старт») | 80 |
| `docs.license` | 0,15 | `bool(есть LICENSE или COPYING)` | 100 |
| `docs.usage_examples` | 0,12 | `bool(есть каталог examples или раздел об использовании в README)` | 100 |
| `docs.contributing` | 0,11 | `bool(есть CONTRIBUTING)` | 100 |
| `docs.changelog` | 0,08 | `bool(есть CHANGELOG или HISTORY.md)` | 100 |
| `docs.docs_dir` | 0,08 | `bool(есть каталог docs/, doc/ или documentation/)` | 100 |
| `docs.code_of_conduct` | 0,06 | `bool(есть CODE_OF_CONDUCT)` | 100 |
| `docs.issue_template` | 0,06 | `bool(есть шаблоны задач или pull request)` | 100 |
| `docs.repo_description` | 0,06 | `bool(описание репозитория в SourceCraft заполнено)` | 100 |

**Оценка модели.** Если рубрика README от модели получена, категория `docs` целиком
определяется её баллом (метрика `docs.ai_rubric`, вес 1). Модель получает до 6000 символов
README и до 80 путей из корня дерева. Критерии: структура, установка, использование,
описание API или конфигурации, сопутствующие документы. Если рубрика не получена,
категория считается по таблице выше.

### 3.5. CI/CD (`ci`)

Источник — наличие конфигурации CI в дереве и текст конфигов из клона. Прогоны берутся
из API SourceCraft `/repos/{org}/{repo}/cicd/runs`, если они доступны.

| Метрика | `w` | Расчёт | Цель |
|---|---:|---|---:|
| `ci.config` | 0,35 | `bool(есть конфиг CI)` | 100 |
| `ci.runs_tests` | 0,25 | `bool(конфиг запускает тесты)` | 100 |
| `ci.pr_checks` | 0,15 | `bool(пайплайн срабатывает на pull request)` | 100 |
| `ci.runs_lint` | 0,10 | `bool(конфиг запускает линтер)` | 100 |
| `ci.runs_success` | 0,15 | `linear(P; 40, 90)`, где `P` — доля успешных среди завершённых последних прогонов, % | 100 |

Правила «нет данных»:

- если конфига CI нет, метрики `runs_tests`, `runs_lint` и `pr_checks` получают «нет данных»,
  и категорию определяет одна метрика `ci.config`. Одно отсутствие CI не превращается
  в четыре штрафа;
- `ci.runs_success` в публичной оценке всегда имеет статус «нет данных»: прогоны SourceCraft
  отдаёт только участникам репозитория. Метрика считается в оценке приватного репозитория и
  в личной оценке владельца.

### 3.6. Задачи (`issues`)

Источник — последние 50 задач репозитория из API SourceCraft.

| Метрика | `w` | Расчёт | Цель |
|---|---:|---|---:|
| `issues.closed_share` | 0,40 | `linear(C; 0, 60)`, где `C` — доля закрытых задач выборки, % | 100 |
| `issues.stale_share` | 0,30 | `inverted(S; 10, 70)`, где `S` — доля открытых задач без изменений дольше 90 дней, %. Если открытых задач нет — 100 | 100 |
| `issues.reaction_time` | 0,30 | `inverted(M; 7, 60)`, где `M` — медиана дней от создания задачи до перевода в работу или закрытия | 100 |

Если задач нет, все три метрики получают «нет данных»: репозиторий не использует трекер,
и это не дефект. Если в работу не взята ни одна задача, «нет данных» получает только
`reaction_time`.

## 4. Агрегация

Обозначения: `m_i` — балл метрики, `w_i` — её вес в категории, `K_k` — множество метрик
категории `k` с данными, `W_k` — вес категории, `K` — множество категорий с данными.

**Балл категории**

```
C_k = Σ_{i ∈ K_k} w_i · m_i  /  Σ_{i ∈ K_k} w_i
C_k = «нет данных», если K_k пусто
```

**Балл до штрафов**

```
S₀ = Σ_{k ∈ K} W_k · C_k  /  Σ_{k ∈ K} W_k
```

**Штрафы**

| Штраф | Размер | Условие |
|---|---:|---|
| `secret_in_code` | 15 | AppSec сообщает об открытом секрете |
| `critical_vuln_unfixed` | 10 | AppSec сообщает об открытой critical-уязвимости без исправленной версии |
| `missing_license` | 8 | Дерево файлов получено, и в нём нет LICENSE |

Штрафы суммируются: `P = Σ penalty`.

**Итог**

```
Score = round(clamp(S₀ − P, 0, 100))
```

Округление выполняется только в самом конце. Баллы категорий хранятся с точностью до десятой.

### Покрытие данных

Рядом с баллом отображается покрытие — доля весов, которые реально измерены:

```
Coverage = Σ_k W_k · (Σ_{i ∈ K_k} w_i / Σ_{i ∈ k} w_i)  /  Σ_k W_k
```

При покрытии ниже 50 % интерфейс предупреждает, что балл основан на малой части данных.
Покрытие не меняет балл. Оно показывает, насколько балл надёжен.

### Пример расчёта

Публичный репозиторий. AppSec недоступен, ИИ-оценки нет. Категории:
`code = 62`, `activity = 71`, `docs = 58`, `ci = 40`, `issues` — нет данных.

```
S₀ = (0,20·62 + 0,15·71 + 0,15·58 + 0,15·40) / (0,20 + 0,15 + 0,15 + 0,15)
   = (12,4 + 10,65 + 8,7 + 6,0) / 0,65 = 37,75 / 0,65 ≈ 58,1
```

LICENSE есть, штрафов нет: `Score = 58`. Категории «Безопасность» и «Задачи» в расчёт
не вошли. Их веса (0,35) распределились между остальными пропорционально.

## 5. Обработка отсутствующих данных

| Ситуация | Результат |
|---|---|
| Источник не ответил (API, клон, AppSec, модель) | Метрики этого источника — «нет данных». Причина записывается в список пробелов анализа и показывается на странице |
| Пустой список получен успешно (задач нет, релизов нет) | Для задач — «нет данных» (трекер не используется). Для релизов — 0: отсутствие подтверждено |
| Дерево файлов не получено | Все метрики наличия файлов — «нет данных». Штраф за LICENSE не применяется |
| Клон не удался или получена только верхушка без истории | Метрики истории — «нет данных». Метрики кода берутся из доступных файлов |
| Категория целиком без данных | Выпадает из итога, её вес распределяется между остальными |
| Нет данных ни по одной категории | Балл 0 с покрытием 0 %. Интерфейс сообщает, что метрики собрать не удалось |

В интерфейсе, Markdown-отчёте и API «нет данных» и ноль всегда отличаются. «Нет данных»
показывается прочерком с подписью. Ноль — числом.

## 6. Публичная и личная оценка

Место в рейтинге не должно зависеть от того, кто запустил оценку. Поэтому оценок две:

- **Публичная.** Строится только на данных, которые SourceCraft отдаёт любому. Её видят в
  рейтинге, бейдже, публичном API и на странице анализа.
- **Личная оценка владельца.** Та же формула, но с данными, доступными только участникам:
  находки AppSec, прогоны CI. Её видит только подтверждённый владелец. В рейтинг она
  не попадает.

Приватный репозиторий оценивается только личной оценкой и никогда не публикуется.

## 7. Рекомендации

Алгоритм подробно описан в [recommendations.md](recommendations.md). Кратко:

- кандидаты — метрики с данными, у которых балл ниже цели;
- для каждого кандидата моделируется исправление: метрика поднимается до цели, итог
  пересчитывается по формуле раздела 4 вместе со снятием связанных штрафов;
- выбирается шаг с наибольшим отношением прироста к трудозатратам, затем выбор повторяется
  с учётом уже выбранных шагов, всего до 12 шагов;
- приоритет: находки безопасности — высокий; прирост от 5 баллов — высокий; от 2 — средний;
  меньше — низкий.

Сумма приростов всех рекомендаций равна разнице между баллом после их выполнения и текущим
баллом. Поэтому обещанный итог никогда не превышает 100.

## 8. Устойчивость методики

| Риск | Как он устранён |
|---|---|
| Второстепенный признак определяет итог | Вес любой метрики в итоговом балле не превышает 0,20 · 0,35 = 7 %, если все категории измерены. Бинарные признаки гигиены (`.editorconfig`, шаблоны задач, code of conduct) весят меньше 1,2 % итога |
| Популярность подменяет здоровье | Лайки, звёзды и форки в балл не входят. Рейтинг по умолчанию сортируется по баллу. Сортировка по лайкам — отдельный режим просмотра |
| Накрутка активности пустыми коммитами | Коммиты и авторы идут по логарифмической шкале: после 50 коммитов и 5 авторов за 90 дней рост прекращается. Активность — 15 % итога |
| Пустые файлы ради галочек | Суммарный вес признаков «файл есть» в документации — 0,72 категории `docs`, то есть не больше 10,8 % итога. При наличии рубрики модели категория оценивается по содержанию |
| Форки и копии шаблонов занимают места | Форки, зеркала, шаблоны и копии шаблонов с историей из одного-двух коммитов получают балл, но не место в рейтинге (`src/lib/rating-eligibility.ts`) |
| Отсутствие данных наказывает за закрытость платформы | Метрики без данных исключаются, веса перераспределяются, покрытие показывается отдельно |
| Недетерминированность модели | Ответы модели кэшируются по хэшу входа (SHA-256). Повторная оценка тех же файлов даёт тот же ответ. Без модели движок работает на детерминированных метриках |

## 9. Контрольные сценарии

Поведение методики закреплено автотестами `src/lib/scoring/__tests__/score.test.ts`
(запуск — `pnpm test`).

| № | Сценарий | Ожидаемое поведение |
|---|---|---|
| 1 | Эталонный репозиторий: все признаки на максимуме | Балл ≥ 95, штрафов нет, все шесть категорий с данными |
| 2 | Пустой репозиторий | Балл ≤ 15, штраф за отсутствие лицензии |
| 3 | Нет данных по истории коммитов | Категория «Активность» — «нет данных», итог не падает до нуля |
| 4 | AppSec: открытый секрет и critical-уязвимость | Штрафы −15 и −10, итог не ниже 0 |
| 5 | Плохие метрики кода при наличии линтера и CI | Категория «Код» снижается |
| 6 | AppSec недоступен | «Безопасность» — «нет данных», рекомендаций по ней нет, справка OSV на балл не влияет |

## 10. Жанр «полезный материал»

Подборки ссылок, конспекты и учебные материалы не оцениваются по шкале «тесты, линтер, CI».
Жанр определяет эвристика (`src/lib/repo-kind.ts`: манифест сборки, доля текстовых файлов,
плотность ссылок в README, характерные слова в названии). Окончательное решение принимает
модель. Для материала вместо балла показывается пометка «Полезный материал» и описание
содержимого. Места в рейтинге по баллу у него нет.
