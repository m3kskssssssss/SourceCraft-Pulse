# Периодический анализ и масштабирование

## 1. Периодичность и её обоснование

Полный анализ стоит дорого: клон, чтение файлов, 4–6 вызовов модели. Большинство
репозиториев за сутки не меняется. Поэтому Pulse разделяет дешёвую проверку «изменился ли
репозиторий» и дорогой пересчёт оценки.

| Процесс | Периодичность | Стоимость | Точка входа |
|---|---|---|---|
| Проверка новых коммитов у всех оценённых репозиториев | 00:00 и 12:00 МСК | один запрос к git-серверу на репозиторий | `POST /api/cron/commit-check`, воркер, админка → «Коммиты» |
| Переоценка репозиториев с новыми коммитами | сразу после проверки | полный анализ | та же точка входа, анализы по три одновременно |
| Обход каталога SourceCraft (`GET /repos`) | раз в 24 ч (`CATALOG_SYNC_HOURS`) | около 275 запросов API, без клонов | `POST /api/cron/catalog`, воркер |
| Пересчёт публичных оценок, изменившихся по дате активности каталога | ежечасно | полный анализ изменившихся | `POST /api/cron/refresh-public`, воркер |
| Оценка ещё не оценённых репозиториев каталога | по кнопке «Старт» в админке → «Каталог» | полный анализ | `POST /api/cron/catalog-run` |
| Пересчёт подтверждённых репозиториев владельцев (бейдж-карточки) | 00:00 по `BADGE_REFRESH_TZ` | полный анализ | `POST /api/cron/refresh-badges`, воркер |
| Синхронизация репозиториев по сохранённым токенам | каждые 5 минут | несколько запросов API | `POST /api/cron/sync-tokens`, воркер |

Проверка коммитов раз в 12 часов гарантирует, что оценка в рейтинге отстаёт от репозитория
не больше чем на полсуток. При этом неизменный репозиторий не пересчитывается.

## 2. Проверка новых коммитов

Реализация — `src/lib/commit-check.ts`, окна проверки — `src/lib/commit-slots.ts`.

1. Для каждого репозитория с готовой оценкой выбирается текущая оценка: опубликованная,
   иначе последняя.
2. Из фактов оценки берётся коммит, на котором она считалась (`headSha`, у старых оценок —
   верхушка ветки по умолчанию из списка веток).
3. Запрос `listServerRefs` к git-серверу возвращает текущую верхушку ветки по умолчанию.
4. Коммиты совпали — в `commit_checks` записывается результат «без изменений». Оценка
   остаётся прежней. В истории оценок появляется отметка «Новых коммитов нет — оценка та же».
5. Коммиты различаются — записывается результат «изменился» и создаётся новый анализ с тем же
   автором и той же публикацией. После успешного завершения новая оценка сменяет прежнюю в
   рейтинге, бейдже и на карточке. Если анализ не удался, прежняя оценка остаётся, повтор —
   в следующем окне.

**Окно проверки.** Окно — 12 часов от ближайших 00:00 или 12:00 МСК. Репозиторий,
проверенный в текущем окне, повторно не проверяется. Поэтому вызов, не успевший проверить
всё за 300 с, дозавершается следующим вызовом, например ежечасным.

**Управление.** Во вкладке админки «Коммиты»:

- кнопка «Проверить сейчас» — внеплановая проверка всех оценённых репозиториев;
- переключатель плановой проверки: выключенная плановая проверка не проверяет и не
  переоценивает;
- сводка текущего окна и журнал последних проверок.

## 3. Статус и время анализа

У каждого анализа хранятся статус (`queued`, `running`, `done`, `failed`), текущая фаза,
время создания и завершения, текст ошибки. На странице анализа и карточке репозитория
показываются дата анализа, дата последней проверки коммитов и история оценок.

**Первичный и повторный запуск.** Повторный анализ того же репозитория создаёт новую запись.
Предыдущая сохраняется в истории с изменением балла. Повторный запуск доступен кнопкой
«Оценить заново» на карточке репозитория и на странице анализа.

## 4. Горизонтальное масштабирование

- **Анализ — отдельная функция.** Каждый анализ выполняется в своём вызове
  `POST /api/analyses/<id>/run` (до 300 с, до 2 ГБ памяти). На Vercel число одновременных
  анализов растёт вместе с числом вызовов.
- **Очередь в PostgreSQL.** Задачу захватывает один исполнитель атомарным `UPDATE … RETURNING`.
  Брошенная задача с блокировкой старше 6 минут возвращается в очередь. Число попыток —
  до трёх.
- **Диспетчеры.** Прогон каталога, пересчёт и переоценки после проверки коммитов держат до
  трёх анализов одновременно. Слоты считаются под advisory-блокировкой PostgreSQL, поэтому
  несколько одновременно вызванных диспетчеров не превышают лимит.
- **Воркеры.** В Docker-варианте `pnpm worker` выбирает задачи через
  `FOR UPDATE SKIP LOCKED`. Можно запустить несколько воркеров: параллельность настраивается
  `WORKER_CONCURRENCY`, размер пачки — `WORKER_BATCH_SIZE`.
- **Ограничение по источникам.** Запросы к API SourceCraft ограничены 8 в секунду, поэтому
  параллельные анализы не выходят за лимит платформы.

## 5. Крупные репозитории

Граница ТЗ: не менее 10 000 файлов, 20 000 коммитов или 500 МБ.

| Приём | Значение |
|---|---|
| Выбор стратегии клона | при 5000 и более записях в дереве — только верхушка без истории |
| Узкий клон | одна ветка, без рабочей копии, окно 90 дней, не глубже 2000 коммитов |
| Резервная попытка | если клон не уложился в 150 с — клон верхушки (depth 1); метрики истории получают «нет данных» |
| Индекс файлов | карта «путь → объект» за один обход дерева, общий кэш isomorphic-git |
| Чтение | до 1500 файлов по кругу из всех каталогов, пачками, с дедлайном; файлы больше 200 КБ пропускаются |
| История | до 2000 коммитов; поиск строк, похожих на ключи, — до 800 файлов |
| Дерево коммитов | полная история догружается только для небольших репозиториев (до 1200 файлов и 300 коммитов) и только при остатке времени |
| Дедлайны фаз | каждая фаза возвращает собранное и помечает себя неполной |

Для проверки подходит публичный репозиторий `iskanderbikta/pointless-go-monolith`,
предложенный участниками хакатона.

## 6. Устойчивость к недоступности источников

| Источник недоступен | Поведение |
|---|---|
| Отдельный эндпоинт API SourceCraft | повтор до трёх раз; затем метрики этого источника — «нет данных», причина в блоке «Что не удалось собрать» |
| Клон | вторая попытка верхушкой; затем метрики кода и истории — «нет данных» |
| AppSec | категория «Безопасность» — «нет данных» |
| OSV.dev | справка не показывается, балл не меняется |
| Модель | категории «Код» и «Документация» считаются по детерминированным метрикам |
| Сбой функции во время анализа | блокировка истекает через 6 минут, задача берётся повторно, до трёх попыток |
| Сбой пересчёта | прежняя оценка остаётся в рейтинге до успешного пересчёта |
